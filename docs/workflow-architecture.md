# Архитектура жизненного цикла договора

Соответствует приложению: `0.7.0-beta`

## Источник истины

Жизненный цикл договора определяется backend-модулем `app/workflows/contract.py`. Frontend не должен самостоятельно восстанавливать этап по набору несвязанных признаков. Каждый ответ сессии содержит объект `workflow`:

```json
{
  "stage": "awaiting_counterparty",
  "stage_label": "Ожидается подпись второй стороны",
  "available_actions": ["sign_counterparty"],
  "action_labels": {
    "sign_counterparty": "Подписать"
  }
}
```

## Этапы

| Этап | Значение |
| --- | --- |
| Черновик | `draft` |
| Версия готова к согласованию | `ready_to_invite` |
| Ожидается подпись второй стороны | `awaiting_counterparty` |
| Ожидается подпись создателя | `awaiting_creator` |
| Договор действует | `active` |
| Открыт спор | `dispute` |
| Договор исполнен | `completed` |
| Удален | `deleted` |

Точный этап пока вычисляется из существующих данных: наличия версии и приглашения, подписей сторон, финализации, спора, исполнения и удаления. Поэтому новая архитектура работает с ранее созданными договорами без миграции базы.

## Правила реализации

1. Новое пользовательское действие сначала добавляется в `ContractAction`.
2. Доступность действия для роли задается только в `STAGE_ACTIONS`.
3. API проверяет действие через `require_workflow_action` до изменения данных.
4. Frontend показывает команды из `available_actions`, а не восстанавливает разрешения самостоятельно.
5. Успешный ответ возвращает обновленный `workflow`, чтобы интерфейс сразу показал следующий шаг.
6. Недопустимый переход возвращает HTTP 409, понятное сообщение и актуальный `workflow`.
7. Любое изменение справочника сопровождается тестом перехода.
